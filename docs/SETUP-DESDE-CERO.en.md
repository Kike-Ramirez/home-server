# Setting up the homelab from scratch

[🇪🇸 Español](SETUP-DESDE-CERO.md) · 🇬🇧 English

Step-by-step guide to deploy the whole stack on a new machine, with no
prior backup. If you already had a backup from a previous system (broken
disk, hardware migration), use
[`RESTAURAR-DESDE-BACKUP.en.md`](RESTAURAR-DESDE-BACKUP.en.md) instead.

The `backups/` scripts assume the repo lives at exactly `/home/home/home`
(it's hardcoded in `backups/backup-common.sh`) — clone it there or adjust
that path before continuing.

## 1. Prerequisites

- A Linux machine with Docker Engine + the `docker compose` plugin installed.
- `python3-yaml` (`sudo apt install python3-yaml`) — used by `daily-report.py`
  to read `grafana/provisioning/alerting/rules.yaml` directly.
- An external USB drive dedicated to backups.
- Your own domain (for Nginx Proxy Manager + Let's Encrypt + Grafana).
- A Zigbee USB dongle (for Home Assistant), plugged in before starting.
- A Tailscale account.
- A Gmail account (or any SMTP server supporting STARTTLS) for
  Vaultwarden/Grafana/daily-report email.
- The `claude` CLI (Claude Code) installed and **logged in** on the machine
  with the user that will run the stack — Sebastián (`telegram-agent/`)
  reuses that session, it doesn't use a separate API key.
- A Telegram bot created via `@BotFather` (`/newbot`) — note the token.

## 2. Clone the repo

```bash
git clone git@github.com:Kike-Ramirez/home-server.git /home/home/home
cd /home/home/home
```

## 3. Configure `.env`

```bash
cp .env.example .env
```

Fill in every variable:

| Variable | Where it comes from |
|---|---|
| `TZ` | Usually fine as `Europe/Madrid`. |
| `PIHOLE_PASSWORD` | Whatever you want for the Pi-hole admin. |
| `VAULTWARDEN_DOMAIN` | The subdomain you'll publish Vaultwarden on. |
| `SIGNUPS_ALLOWED` | `false` unless you want open sign-up. |
| `VAULTWARDEN_ADMIN_TOKEN` | `openssl rand -base64 48` |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | Gmail account + [app password](https://myaccount.google.com/apppasswords). |
| `GF_SECURITY_ADMIN_USER` / `GF_SECURITY_ADMIN_PASSWORD` | `admin` + `openssl rand -base64 24` — prevents Grafana from ending up on `admin/admin` if the `grafana_data` volume is ever recreated. |
| `TS_AUTHKEY` | Tailscale admin console → Settings → Keys → generate a reusable auth key. **Once the node is authenticated and `docker compose ps tailscale` shows it `healthy`** (state persists in `tailscale/state/`, it won't need the key again unless that state is wiped), revoke it from the console and clear `TS_AUTHKEY=` in `.env` — leaving it alive indefinitely in plain text is an "add a device to my tailnet" secret with no real need. |
| `BACKUP_TRIGGER_TOKEN` | `openssl rand -hex 32` — used by the "Backups" dashboard to call the webhook. |
| `TELEGRAM_API_TOKEN` | The one `@BotFather` gave you when creating the bot. |
| `TELEGRAM_CLIENT_ID` | The chat_id of the Telegram group/chat you want alerts + Sebastián in — see step 9, filled in at the end. |
| `ANTHROPIC_API_KEY` | Not needed for Sebastián (he uses the already-authenticated `claude` CLI); only needed if you also set up HA's native "Anthropic Conversation" integration from its UI. |

## 4. Prepare files/directories not tracked in git

All of this is in `.gitignore` on purpose (it's runtime data or secrets):

```bash
mkdir -p pihole/etc-pihole vaultwarden/data \
  nginx-proxy-manager/data nginx-proxy-manager/letsencrypt \
  tailscale/state

# Backup encryption password -- SAVE IT SOMEWHERE ELSE TOO (password
# manager, paper, etc.). Without it, the encrypted backups are
# unrecoverable.
openssl rand -base64 32 > backups/restic-password.txt
chmod 600 backups/restic-password.txt
```

`homeassistant/config/secrets.yaml` will be generated by HA on first boot
if it doesn't exist; if you need it earlier (e.g. for Telegram, see step 9),
create it yourself with the keys you're missing.

## 5. Mount the backups drive and initialize restic

```bash
# Mount your USB drive at /media/home/home-backups (fstab or by hand), then:
mkdir -p /media/home/home-backups/home-backups

docker run --rm \
  -v /media/home/home-backups/home-backups:/repo \
  -v "$(pwd)/backups/restic-password.txt:/repo-password:ro" \
  -e RESTIC_REPOSITORY=/repo -e RESTIC_PASSWORD_FILE=/repo-password \
  restic/restic:latest init
```

## 6. Bring up the stack

```bash
docker compose config -q   # validates syntax
docker compose up -d
docker compose ps          # everything "healthy" or "running" within a few minutes
```

## 7. Home Assistant: long-lived token

Once HA has booted (`http://<host-ip>:8123`), complete the initial setup
wizard and create your user. Then:

1. Profile (user icon) → "Security" tab → "Long-Lived Access Tokens" → create one.
2. Save the value to `prometheus/ha-token.txt` (no extra trailing newline):
   ```bash
   echo -n "<token>" > prometheus/ha-token.txt
   ```
   It's used by both Prometheus (`/api/prometheus`) and Sebastián's tools.
3. `docker compose restart prometheus` so it picks it up.

## 8. Nginx Proxy Manager + domain

Go to `http://<host-ip>:81` (default credentials on first login, it will
ask you to change them), add your proxy hosts (Grafana, Vaultwarden, etc.)
pointing to the containers by name (`grafana:3000`, ...), and request the
Let's Encrypt certificates from there.

## 9. Telegram: bot, group, and Sebastián

1. Create a Telegram group with whoever's going to talk to Sebastián, add
   the bot as a member.
2. Turn off its "privacy mode" so it sees every message in the group (not
   just commands/mentions): `@BotFather` → `/mybots` → your bot → `Bot
   Settings` → `Group Privacy` → `Turn off`.
3. Send any message in the group and check the chat_id:
   ```bash
   curl -s "https://api.telegram.org/bot<TELEGRAM_API_TOKEN>/getUpdates" | python3 -m json.tool
   ```
   Look for `"chat":{"id": ...}` (negative, it's a group) and put it in
   `TELEGRAM_CLIENT_ID` in `.env`.
4. Set up Sebastián's environment:
   ```bash
   cd telegram-agent
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   deactivate
   ```
5. Install and start the systemd service:
   ```bash
   sudo cp sebastian-bot.service /etc/systemd/system/sebastian-bot.service
   sudo systemctl daemon-reload
   sudo systemctl enable --now sebastian-bot
   sudo systemctl status sebastian-bot --no-pager
   ```
6. `docker compose restart grafana` (so it picks up
   `TELEGRAM_API_TOKEN`/`TELEGRAM_CLIENT_ID` and can send alerts over
   Telegram).

## 10. Backups webhook as a systemd service

`webhook-server.py` runs on the **host** (not containerized, on purpose,
to avoid Docker-in-Docker when it launches restic's `docker run`) and
exposes `backup-now`/`restore`/`restore-confirm` for the "Backups"
dashboard. It's managed with systemd instead of `@reboot`/`nohup` so it
restarts on its own if it dies:

```bash
sudo cp backups/webhook-server.service /etc/systemd/system/webhook-server.service
sudo systemctl daemon-reload
sudo systemctl enable --now webhook-server
sudo systemctl status webhook-server --no-pager
curl -s http://localhost:8088/healthz
```

`EnvironmentFile=/home/home/home/.env` in the unit gives it access to
`BACKUP_TRIGGER_TOKEN` (and the rest of `.env`, just like `docker compose`
does) — adjust that path if you didn't clone the repo at `/home/home/home`.

## 11. Automatic system maintenance (Ubuntu)

This is **host** config, not part of the repo (nothing to version-control
here beyond what's already in `backups/docker-prune.sh` and the crontab in
the next step). It's needed for two things: the OS updating itself (not
just the containers), and getting an email if something fails.

### 11.1 Automatic security updates (`unattended-upgrades`)

Why: without this, OS security patches (kernel, OpenSSL, etc.) only get
applied if you run `apt upgrade` by hand. On a machine running services
exposed to the internet (Nginx Proxy Manager, Vaultwarden), it's worth
having at least the security patches apply themselves.

```bash
sudo apt install unattended-upgrades apt-listchanges
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

This writes `APT::Periodic::Unattended-Upgrade "1";` to
`/etc/apt/apt.conf.d/20auto-upgrades`. No dedicated timer needed: it's
triggered by APT's own systemd timers (`apt-daily.timer` to refresh the
index, `apt-daily-upgrade.timer` to apply updates) — already shipped with
the `apt` package, check they're active:

```bash
systemctl list-timers | grep apt
```

Fine-tune it in `/etc/apt/apt.conf.d/50unattended-upgrades` (by default it
only updates the `-security` repo; adjust `Allowed-Origins` and
`Automatic-Reboot` if you want more, or automatic reboots after kernel
updates).

### 11.2 Email alert if `unattended-upgrades` fails

Why: without a local MTA, `unattended-upgrades` has no way to send mail
even if you ask it to in its config — it needs something behind the
`/usr/sbin/sendmail` binary. We reuse the Gmail SMTP already in `.env`
(the same one used by Grafana/Vaultwarden/`daily-report.py`), instead of
setting up a full Postfix.

```bash
sudo apt install msmtp msmtp-mta
```

Create `/etc/msmtprc` (use the `SMTP_USERNAME`/`SMTP_PASSWORD` credentials
from your `.env`):

```
defaults
auth           on
tls            on
tls_trust_file /etc/ssl/certs/ca-certificates.crt
logfile        /var/log/msmtp.log

account        gmail
host           smtp.gmail.com
port           587
from           <SMTP_USERNAME>
user           <SMTP_USERNAME>
password       <SMTP_PASSWORD>

account default : gmail
```

```bash
sudo chown root:root /etc/msmtprc
sudo chmod 600 /etc/msmtprc
```

`msmtp-mta` already points `/usr/sbin/sendmail` to `msmtp` — no need to
touch `update-alternatives`.

Then, in `/etc/apt/apt.conf.d/50unattended-upgrades`:

```
Unattended-Upgrade::Mail "<your-email>";
Unattended-Upgrade::MailReport "only-on-error";
```

**AppArmor confines the `msmtp` binary** (the package's own profile) and by
default won't let it create or lock its own logfile outside the paths the
profile ships with — you'll see something like
`apparmor="DENIED" operation="mknod"` or `operation="file_lock"` on
`/var/log/msmtp.log` in `dmesg`. Grant it explicit permission with a local
override (don't edit the package's profile directly, it'd get overwritten
on updates):

```bash
echo '/var/log/msmtp.log rwk,' | sudo tee -a /etc/apparmor.d/local/usr.bin.msmtp
sudo apparmor_parser -r /etc/apparmor.d/usr.bin.msmtp
```

Note: `rw` without the `k` isn't enough — `msmtp` does an `flock()` on the
logfile before writing, and AppArmor treats the lock permission (`k`)
separately from read/write.

Verify it actually sends mail (as root, since that's who runs
`unattended-upgrades`):

```bash
sudo msmtp -a gmail <your-email> <<< "Test unattended-upgrades"
echo "exit=$?"   # should be 0, with no message from msmtp
```

### 11.3 Log rotation for `backups/` and Sebastián

Why: `backup.log`, `webhook-server.log`, `daily-report.log`, etc. grow
without bound if nothing rotates them — `backups/logrotate.conf`
(version-controlled) covers every `backups/*.log` plus
`telegram-agent/agent.log`.

```bash
sudo cp backups/logrotate.conf /etc/logrotate.d/homelab
sudo logrotate -d /etc/logrotate.d/homelab   # dry-run, validates the config
```

Weekly, 8-week history, compressed. The config's `su home home` is needed
because `backups/` is `775` (not only writable by root) — logrotate
refuses to rotate there without being told explicitly which user/group to
use. Triggered by the daily cron Ubuntu already ships
(`/etc/cron.daily/logrotate`), no dedicated cron entry needed.

## 12. Offsite backup on Google Drive (3-2-1)

Why: the local backups USB drive is a single physical point of failure
(theft, fire, drive failure at the same time as the server). A copy of
the `monthly-full` snapshots (the ones you already keep forever) is sent
to a second, independent restic repo on Google Drive — only those, not
the `nightly` ones, to avoid burning extra bandwidth/storage.

You need `restic` natively on the host (not the `restic/restic` container,
that image doesn't ship the rclone backend) and `rclone`:

```bash
sudo apt install rclone
# native restic: https://github.com/restic/restic/releases, or
# curl -fsSL https://raw.githubusercontent.com/restic/restic/master/install.sh | sh
```

Configure the remote (needs a browser for OAuth):

```bash
rclone config   # new remote "gdrive", type "drive"
```

**Use your own OAuth credentials**, not rclone's shared default ones — the
shared Google Drive API quota gets exhausted quickly with every rclone
user in the world behind it (constant `rateLimitExceeded`, confirmed in
production). In the [Google Cloud
Console](https://console.cloud.google.com/): create a project → enable the
**Google Drive API** → "Credentials" → "Create Credentials" → "OAuth
client ID" → type **Desktop app** → copy the `Client ID`/`Client secret`
and paste them into `rclone config` (edit the `gdrive` remote, the
`client_id`/`client_secret` fields, then `rclone config reconnect
gdrive:` to re-authorize with the new credentials).

Initialize the offsite repo (same password as the local repo):

```bash
RESTIC_REPOSITORY=rclone:gdrive:home-backups-offsite \
RESTIC_PASSWORD_FILE=backups/restic-password.txt \
restic init
```

`backups/backup-offsite.sh` runs `restic copy --tag monthly-full` from the
local repo to this one. The first time it uploads everything from scratch
(it can take a while, and you'll see occasional retries for
`rateLimitExceeded` — that's normal, Drive's file-creation endpoint has
its own limit separate from the project's general quota); run it by hand
once before relying on the cron:

```bash
backups/backup-offsite.sh
tail -f backups/backup-offsite.log
```

## 13. Crontab

```bash
crontab -e
```

Paste exactly this (only adjust the paths if you didn't clone into
`/home/home/home`):

```cron
30 3 * * * /home/home/home/backups/backup.sh
0 0 1 * * /home/home/home/backups/backup-monthly.sh
30 1 1 * * /home/home/home/backups/backup-offsite.sh
0 2 15 * * /home/home/home/backups/restic-check.sh
*/5 * * * * /home/home/home/backups/network-metrics.sh
* * * * * /home/home/home/backups/container-health-metrics.sh
0 8 * * * /usr/bin/python3 /home/home/home/backups/daily-report.py >> /home/home/home/backups/daily-report.log 2>&1
0 4 * * 0 /home/home/home/backups/docker-prune.sh
```

(the backups webhook no longer runs via cron — see step 10, it now runs as
a systemd service.)

## 14. Final verification

- `docker compose ps` — everything up and "healthy".
- Grafana reachable at your domain, dashboards loaded (`grafana/provisioning/dashboards/`).
- `systemctl status sebastian-bot` — `active (running)`.
- Write to the bot in the Telegram group and confirm it responds.
- `systemctl status webhook-server` — `active (running)`; `curl http://localhost:8088/healthz` returns 200.
- Trigger a test backup: `backups/backup.sh` by hand and check `backups/backup.log`.
- Confirm the daily report arrives, or wait for the 08:00 cron.
- `sudo msmtp -a gmail <your-email> <<< "test"` with no errors — confirms
  `unattended-upgrades` will be able to email you if something fails.
- `RESTIC_REPOSITORY=rclone:gdrive:home-backups-offsite RESTIC_PASSWORD_FILE=backups/restic-password.txt restic snapshots` shows at least one `monthly-full`.
- `sudo logrotate -d /etc/logrotate.d/homelab` with no errors (`insecure permissions`, etc.).
